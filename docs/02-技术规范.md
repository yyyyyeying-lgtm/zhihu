# 02 · 技术规范

> 技术选型已经锁定。**要改选型，必须先在日志里写清楚理由，并得到用户明确同意。**

---

## 一、技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 形态 | 纯静态本地网页应用 | 用户非技术背景，双击即用的优先级高于一切 |
| 语言 | 原生 HTML + CSS + JavaScript | 无编译、无依赖，改一行刷新就见效 |
| 模块方式 | 传统 `<script>` 标签（**不用 ES Module**） | `file://` 协议下 ES Module 会被 CORS 拦掉，整个应用打不开 |
| 数据 | 内置 JS 常量 + `localStorage` | 没有后端，也就不需要网络请求 |
| 依赖 | **零** | 见下面的红线 |
| 构建 | **无** | 没有 npm、没有打包、没有产物目录 |

### 为什么不换（被否掉的方案）

| 备选 | 否掉的理由 |
|---|---|
| Electron / Tauri 打包成原生 App | 体积大、可能被系统安全策略拦；收益只是"看起来像原生"，对非技术用户反而增加安装风险 |
| React / Vue 前端框架 | 引入构建链路后，用户就无法"自己打开文件改一个字"了；本项目页面量级完全不需要 |
| 引入 UI 组件库 | 本项目全是定制化的"文书卡片"，组件库能提供的部分不到 20% |

### 三条红线

1. **不引入任何 npm 依赖**（包括 CDN 引入的库）。如果确实需要，先停下来问用户。
2. **不使用 ES Module / `import` / `fetch` 本地文件**。应用必须能在 `file://` 协议下直接打开。
3. **不需要任何构建步骤**。源码即产物。

### 跨文件共享的对象必须显式挂 `window`（踩过，代价很大）

顶层 `const` / `let` / `class` 声明**只进全局词法环境，不会成为 `window` 的属性**。
本项目因此出过一个静默失效的缺陷：`ai.js` 用 `const ZHILIAO_AI = ...`，
而 `app.js` 的守卫写 `window.ZHILIAO_AI`，条件永远为假 —— 真实 AI 从未被调用过，
界面上却看不出任何异常。

**规矩**：任何被其他文件引用的全局对象，导出时都显式挂一次：

```javascript
const ZHILIAO_AI = (() => { /* ... */ })();
if (typeof window !== 'undefined') window.ZHILIAO_AI = ZHILIAO_AI;
```

并且**同一个对象不要在项目里出现两种引用写法**（`X` 和 `window.X` 混用是这类 bug 的温床）。

## 四、代码组织原则

### 4.1 全局状态只有一个

所有运行时状态集中在 `app.js` 顶部的 `S` 对象里，**不散落**。

```javascript
S = {
  step,          // 当前进度（0-5，对应 RAIL 下标）
  question,      // 用户主诉
  answers,       // 问诊记录
  chart,         // 病历首页
  wound,         // 用户确认的病灶
  map,           // 分歧地图
  experts,       // 会诊参与者
  testimonies,   // 异步证言
  panel,         // 合议消息
  conclusion,    // 会诊结论书
  plan, planNote,// 行动清单
  usedAI,        // 本次是否走了真实 AI
  note           // 降级提示
}
```

新增字段：先在 `freshState()` 里给默认值，再使用。**不要临时挂全局变量。**

### 4.2 每个流程阶段一个 `runXxx()` 函数

主流程是一串顺序调用的阶段函数，每个负责"渲染 + 等待用户输入 + 调用下一个"：

```
start() → onRegister() → runAsk() → runChart() → runMap()
        → runInvite() → openRoom() → runConclusion() → runPlan()
```

新增阶段的规矩：
- 函数名 `run` + 阶段名，必须 `async`
- 需要用户操作时用 `Promise` 包装点击，不要在函数里轮询 DOM
- 阶段结束时调用下一个阶段，**不要写回调嵌套**

### 4.3 渲染一律用字符串模板

不引模板引擎，也不手写 `createElement` 拼装（除少数需要绑事件的场景）：

```javascript
function docCard(tag, title, sub, inner) {
  return node('<div class="doc-card">' + ... + '</div>');
}
```

- `node(html)` 把字符串变成 DOM 节点
- `attach(el)` 追加到 `#stream` 并加 `.rise` 入场动画
- **所有来自数据的文本必须过 `esc()`**，防止 HTML 注入与显示错乱

### 4.4 文书卡片用统一的工厂函数

新增一种"文书"（比如 v1.1 的会诊手记）时，**沿用 `docCard()`**，不要另写一套：

```javascript
docCard('⑦ 会诊手记', '会诊手记', '公开 · 归属创作者', innerHtml)
```

参数顺序固定：`(标签, 标题, 副标题, 内容 HTML)`。标签用带圈数字表示流程顺序。

## 五、数据契约（`data.js`）

`data.js` 只导出**一个全局常量** `ZHILIAO_DATA`。换一个演示案例时，只改这个文件，不动其他任何代码。

**案例结构（v1.2 起）**：`cases` 是一个**以案例 id 为键的对象**，每个案例自带 `verdict`
（判定档位）与 `match`（命中关键词）。用户挂号后由 `pickCase()` 按关键词命中数选用案例，
命中不足时用 `defaultCase` 兜底。

### 顶层字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `examples` | `string[]` | 首页示例困惑。**三个示例各对应一条判定分支**，方便一眼看到三档判定的差别 |
| `verdicts` | `{id, label, sub}[]` | 三档判定的三个选项（全局共用，不要在各案例里重复定义） |
| `defaultCase` | `string` | 关键词命中不足时的兜底案例 id |
| `cases` | `{ [id]: Case }` | 案例库 |
| `seedRecords` | `object[]` | 「我的病例」预置的历史记录 |
| `greeting` | `string[]` | 狐看山医生的开场白 |

### 案例字段（`cases[id]`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `string` | 与键名一致 |
| `verdict` | `'settled' \| 'dispute' \| 'insufficient'` | **这条案例走哪条分支**，决定流程走向与进度轨 |
| `match` | `string[]` | 命中关键词，与用户输入做包含匹配（忽略大小写） |
| `receipt` | `{client, chief, dept, tag, advice}` | 挂号单文案。**科室与并发症由这里提供**，不再按关键词分诊 |
| `asks` | `{q, chips[]}[]` | 问诊追问与快捷选项，恰好 2 条 |
| `chart` | `{chief, history, variables[], hypotheses[]}` | 病历首页；`hypotheses` 恰好 3 条 |
| `map` | `{topic, corpus, current, conclusion, disputes[], consensus[], sparse[], plan[], planNote}` | 分歧地图。后两项只在 `current === 'settled'` 时使用 |
| `plan` | `{when, what}[]` | 行动清单，恰好 4 条 |
| `planNote` | `string` | 回访提示 |

### 只有 `verdict: 'dispute'` 的案例才需要的字段

| 字段 | 说明 |
|---|---|
| `experts` | 会诊参与者，恰好 4 位 |
| `testimonies` | 异步证言，`author` 对应 `experts[].id` |
| `panel` | 合议消息，`who` 为 `'host'` 或 `experts[].id` |
| `conclusion` | 会诊结论书 |
| `handnotes` | 会诊手记，恰好 4 条 |

### 只有非 dispute 案例才需要的字段

| 字段 | 所属分支 | 说明 |
|---|---|---|
| `map.consensus` | `settled` | 共识条目 `{name, support, bar, meta}`，用于替代 `disputes` |
| `map.sparse` | `insufficient` | 零散讨论 `{name, levelText, bar, meta}`，用于替代 `disputes` |
| `settled` | `settled` | 已确诊结论 `{title, byline, points[], note}` |
| `draft` | `insufficient` | 提问草稿 `{title, lead, body, whyTitle, hints[], button}` |

> **`findings` 的三套结构由 `findingRows()` 统一成同一套渲染结构** —— 这也是为什么
> `disputes` / `consensus` / `sparse` 可以共用同一段 DOM 模板。新增判定档位时，
> 只需要在 `findingRows()` 里加一条映射。

### AI 返回的结构约定（v1.5）

`ai.js` 的三个推理函数必须返回**与上面案例字段同构**的对象，`app.js` 才不需要为
「演示」和「真实 AI」写两套渲染：

| 函数 | 必须返回 |
|---|---|
| `chart()` | `{dept, tag, chief, history, variables[], hypotheses[3]}` |
| `disputes()` | `{topic, corpus, current, conclusion, disputes[], consensus[], sparse[], plan[], planNote, draft}` —— **一次调用覆盖三条分支**，只填 `current` 对应的那一组 |
| `conclusion()` | `{title, consensus[3], dispute, dissent, plan[4], planNote}` |

> **为什么 `disputes()` 要一次给出三组内容**：判定结果决定流程走向，如果判定和内容
> 分两次拿，就可能出现「判定为已确诊，返回的却是分歧清单」这种错位。
> 一次调用同时产出，判定与内容天然一致。

### 硬约束

- **走哪条分支以 `S.map.current` 为准，不是 `S.case.verdict`**。`verdict` 只是挂号时
  用关键词做的「预判」；真实 AI 模式下必须让检测结果覆盖它（`runMap()` 里回写
  `S.verdict` 与 `S.rail`）。否则会出现「界面高亮已确诊、流程却去开了会诊」这种自相矛盾
- `consensus[].src` **必须**填来源计数（如 `4/4 位参与者一致`），**不许留空、不许编造**
- `conclusion.dissent` 必须来自 `panel` 里真实表达过异议的人，**不能虚构**
- `experts` 恰好 4 位，且观点必须分成两派（否则"分歧"这个卖点不成立）
- **`handnotes` 恰好 4 条，与 `experts` 一一对应；`excerpt` 只能由该专家自己的
  `testimonies` 与 `panel` 发言重组而成，保留其原话中的具体数字，一个字都不许新增**
- **每个案例的 `verdict` 必须与 `map.current` 一致**，否则流程会串线（脚本会检查）
- 任何新增字段都要在本表里登记，否则下次换案例的人不知道该填什么

## 五点五、知乎数据开放平台接入约定（`zhihu.js`）

| 项 | 约定 |
|---|---|
| 端点 | `GET https://developer.zhihu.com/api/v1/content/zhihu_search?Query=&Count=`（Count 上限 10） |
| 鉴权 | `Authorization: Bearer <AccessSecret>` ＋ **`X-Request-Timestamp`（秒级时间戳，必传）** |
| 跨域 | 官方已开 `access-control-allow-origin: *`，**纯静态应用可直连，不需要后端中转** |
| Key 存放 | `localStorage`，key 名 `zhiliao_zhihu_config`。**绝不上传** |
| 错误判定 | **HTTP 200 不代表成功** —— 业务错误码在 body 里（`Code=20001` 是鉴权失败，`30001` 是限流）。只看 `res.ok` 会误判 |
| 解析容错 | 官方字段名可能变化，`normalize()` 里对每个字段都写了多种写法兼容；结构变了也不会整条链路失效 |
| 降级 | 未配置 / 检索为空 / 调用失败，三种情况都回退内置语料，并由 `corpusTag()` 在界面上标出用的是哪一种 |
| 免费额度 | 需实名认证，1000 次/天（未实名 10 次/天） |

> **两类标注不要混**：`sourceTag()` 说的是「判定和内容是谁推理的」，
> `corpusTag()` 说的是「这些讨论是从哪来的」。两张都要标，才能一句话讲清一张卡的可信度。

### 新增一条外部数据链路的规矩

1. 新开一个文件（如 `zhihu.js`），**不要塞进 `ai.js`** —— 一个文件一种外部能力
2. 结尾**必须**显式 `window.X = X`（顶层 `const` 不会挂到 window，这个坑已经吃过一次）
3. 鉴权头、错误码、降级、界面标注，四件事缺一不可
4. 验证用**注入假 `fetch`**，不要用真凭证（会泄漏、不稳定、还要看额度）

## 六、AI 接入约定（`ai.js`）

| 项 | 约定 |
|---|---|
| 协议 | OpenAI 兼容的 `/chat/completions` |
| 支持的服务商 | DeepSeek / 智谱 / Kimi / 通义 / OpenAI / 自定义 |
| Key 存放 | `localStorage`，key 名 `zhiliao_ai_config`。**绝不上传到任何地方** |
| 开关 | 设置面板「演示剧本 / 接入真实 AI」。**默认必须是演示模式** |
| 超时 | `chat()` 内置 `AbortController`，默认 90 秒（可用 `opts.timeout` 覆盖）。网络不通时必须自己断开，不能让用户永远停在「正在会诊…」 |
| 降级 | 任何 AI 调用失败，**必须**回退到内置数据，并调用 `noteDegrade(步骤名, err)` 记录；**同时贴在对应卡片上让用户看见**（`degradeNotice()`）。只写 `console.warn` 不算数 |
| 来源标注 | 每张推理卡都调 `sourceTag()`，标出「真实 AI 推理 / 内置示例数据 / 已降级」三态之一 |
| 对外接口 | `chart()` / `disputes()` / `conclusion()` / `ping()`，以及通用的 `chat()` / `json()` |

### 新增 AI 能力的规矩

1. 在 `ai.js` 里加一个语义化函数，返回**结构化对象**（不是字符串）
2. 提示词必须要求输出 JSON，并用 `stripJson()` 兜底解析
3. 在 `app.js` 里调用时**必须**包 `try/catch`，`catch` 里**必须**调 `noteDegrade()`，
   失败走内置数据。**静默降级是被禁止的** —— 用户以为在看真实 AI 的结果，
   实际看的是内置示例，这比直接报错更糟
4. 界面上要能区分"真跑"和"模拟"——这是方案 §8.2 的要求，也是答辩时的加分项。
   新增推理卡时，卡片顶部要带上 `sourceTag()` 与 `degradeNotice()`
5. **判定类接口必须让结果真正驱动流程**：不能用「调用成功与否」当判定条件
   （`out.disputes.length` 会漏掉本来就没有分歧清单的 settled / insufficient）

## 八、给 `app.js` 加功能的落点指引

| 想做什么 | 改哪里 |
|---|---|
| 加一个新流程阶段 | 新增 `runXxx()`，在 `RAIL` 里加一项，在上一阶段结尾调用它 |
| 加一种新文书卡 | 用 `docCard()` 生成，追加到 `#stream` |
| 改会诊室内容 | 只改 `data.js` 的 `testimonies` / `panel`；要改播放逻辑才动 `playTestimonies()` / `playPanel()` |
| 加一个设置项 | `index.html` 的弹窗里加字段 → `initSettings()` 里绑定 → `ZHILIAO_AI.set()` 持久化 |
| 加一条持久化数据 | `localStorage`，key 用 `zhiliao_` 前缀，读写都包 try/catch |
