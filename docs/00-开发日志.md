## 2026-09-12 ｜ v1.9 ｜ 手机适配：让评委在手机上也能打开

**本次范围**：`css/app.css` 的响应式区块 + `app.js` 一个 URL 参数。**桌面端一行未改。**

**做了什么**

- `css/app.css`：新增 720px / 430px 两个断点（保留原有 860px），补齐三处关键修复
  - 输入区改纵向，挂号按钮全宽 —— 原来两者挤一行，窄屏下按钮被挤出可视区
  - 会诊室头部改纵向，阶段指示器独占一行 —— 原来标题被压到竖排成一列单字
  - 顶栏允许收缩但禁止折行
  - 补上若干容器的 `min-width: 0`
- `js/app.js`：支持 `?demo=1`，打开链接即自动播放演示
- `tools/verify.sh`：新增「手机宽度检测」段与 3 项断言

**为什么这么做**

给项目按官方四维度打分时意识到一个被忽略的场景：**评委收到链接，很可能先用手机点开。**
实测下来，375px 下会诊室的标题会竖排成一列、顶栏折行、挂号按钮跑出可视区 ——
这种表现会被直接判「不可用」，而完成度占 25% 权重。

> 🐞 **[差点犯错] 用 `--window-size=390` 测窄屏，结论是错的**
>    现象：截出来的图里挂号按钮不见了，看起来是横向溢出。
>    原因：**Chrome 无头模式的最小视口是 500px** —— 请求 390 会被静默提升到 500，
>          截出来的其实是「500px 布局裁到 390 宽」，按钮在 394px 处，被裁掉了而已。
>    修法：**用 iframe 当容器**。iframe 内部 `innerWidth` 就是 375，媒体查询也按 375 生效。
>    影响：如果我按那个错误诊断去做，会去修一个不存在的问题，
>          而真正的问题（会诊室头部 flex 不肯让步）反而可能被漏掉。

**实施中的关键决策**

1. **宁可换行，不要硬挤**。会诊室头部的病根是 flex 子项默认 `min-width: auto`：
   内容多的撑破容器、设了 `min-width: 0` 的又被压到极限。解法不是调数值，是让它换行。
2. **桌面端必须零变化**。所有规则包在 `@media` 里，改完用新旧截图**逐像素对比**确认
   差异区域为空 —— 这比肉眼看可靠。
3. **窄屏验证没法靠 dump-dom**（拿不到 iframe 内部），所以让测试页把检测结果写进
   **父页面的 title**，再让 verify.sh 从 title 里读。

**验证情况**

```
✓ 静态检查通过（41 个 id）
✓ 手机检测：home:vw=375,overflow=0 | room:vw=375,overflow=0
✓ 桌面端 1180px 新旧截图逐像素对比：差异为空
✓ 81 项断言全绿（11 组）
```

**遗留问题 / 下一步候选**

- 平板竖屏（768px）未单独验证，理论上走 860px 那档规则
- 横屏手机（高度很小时）未验证
- 无障碍（键盘走完主流程、aria 标注）仍未做 → v2.1

## 2026-09-12 ｜ v1.7 + v1.8 ｜ 接上知乎官方数据源，并修掉「评委不会用」

**本次范围**：用户给出 https://developer.zhihu.com/ 这个入口，要求接入真实数据。
接入过程中顺带发现并修掉了一个演示可用性缺陷。

**做了什么**

- 新增 `知了诊所/js/zhihu.js`：知乎数据开放平台的独立接入模块
- `index.html`：引入新模块；设置面板新增「知乎官方数据源」区块（AccessSecret + 测试连接）
- `js/app.js`：`runMap()` 优先用 `zhihu_search` 取真实站内讨论，并传给 AI 做聚类；
  新增 `corpusTag()` / `searchQuery()` / `realPostsHTML()`
- `js/app.js`：首屏新增「直接看一次完整演示」入口（v1.8）
- `js/ai.js`：`disputes()` 支持接收真实语料，提示词要求"只基于这些内容判断"
- `css/app.css`：新增 `.src-tag.corpus` / `.real-list` / `.wd-btn` 等
- 工具：`drive.js` 加 T=60 / T=61 两个阶段，`verify.sh` 加 13 项断言

**为什么这么做**

**（一）我原来的判断错了，而且错得很关键。**
方案的「已知限制」里一直写着"知乎没有对外开放的内容 API"。核实后发现平台确实提供
站内搜索 / 全网搜索 / 热榜 / 知答，**而且开了跨域**。
这意味着：分歧地图可以从"离线语料"变成"真实检索"—— 直接补上了评分里权重最高的
「与知乎生态的契合度」这一栏最薄的地方。

**（二）顺带发现一个演示可用性缺陷。**
给项目按官方四维度打分时意识到：把链接给评委，他打开看到的是输入框，
**不知道要按 `P`**。说明书里写了，但评委不一定读。
结果是产品最强的能力（自动演示）藏在一个没人知道的快捷键后面。所以加了首屏入口。

关键决策：

1. **先实测跨域，再决定架构**。OPTIONS 预检确认 `access-control-allow-origin: *`
   才敢用纯静态方案。否则整个方案要改成"加后端中转"。
2. **`X-Request-Timestamp` 必传**，漏了直接鉴权失败 —— 实测踩到，写进文档。
3. **业务错误码藏在 HTTP 200 的 body 里**（`Code=20001` 是鉴权失败）。
   只看 `res.ok` 会误判成成功 —— 这是第二次踩"HTTP 成功≠业务成功"。
4. **解析器写成容错的**。官方返回结构没有公开稳定文档，每个字段都做多写法兼容，
   万一结构不同也不会整条链路失效。
5. **只接数据、没接 AI 时不假装做聚类**。如实列出原始讨论并说明判定仍来自内置示例。
   **半真半假比全假更危险** —— 它更不容易被发现。
6. **AccessSecret 不做后端中转**。跨域已开，纯静态直连即可；
   密钥只存本机 localStorage，沿用现有 AI Key 的模式。

**遗留的诚实说明**

- 我**没有** AccessSecret，无法端到端实测真实接口。代码路径用注入的假 `fetch` 验证过，
  但真实返回结构需要用户拿到 Secret 后实测一次；解析器已做容错，
  如果字段对不上，改 `normalize()` 里的字段名列表即可。

**验证情况**

```
✓ 静态检查通过（41 个 id）
✓ 21 个阶段截图 + 10 份 DOM 快照
✓ 78 项断言全绿（10 组）
```

新增的 13 项里最关键的是这四条：
- 只接数据时标注了真实来源 / 如实说明判定仍是内置的
- **真实条数被送进了模型**（`知乎 5 条相关讨论`）
- **聚类里用了真实的作者与赞数**（`测试作者甲 3421 赞`）
- 做了聚类就不再堆原始列表

**遗留问题 / 下一步候选**

- 用户创作 / 收藏列表接口（对应"观点指纹"）已由平台提供，未接入
- 知答 API 兼容 OpenAI 协议，可作推理模型，未接入
- 用户访谈（唯一短板）：已写好工具包 `提交材料/知了诊所-用户访谈工具包.md`

## 2026-09-12 ｜ v1.6 ｜ 结案产出可以带走

**本次范围**：`docs/04` 的 v1.6。纯前端的产出导出，不碰流程逻辑与数据结构。

**为什么这么做**

## 2026-09-12 ｜ v1.5 ｜ 真实 AI 的正确性与容错：别让「争议检测」变成摆设

**本次范围**：`docs/04` 的 v1.5。真实 AI 通路的正确性与容错，纯代码，不碰演示模式的分支逻辑。

**做了什么**

- `js/ai.js`
  - `disputes()` 的输出扩展成**一次覆盖三条分支**：`current` + `disputes` / `consensus` /
    `sparse` / `plan` / `draft`，只填 `current` 对应的那一组
  - `chat()` 加 `AbortController` 超时（默认 90 秒），并把"连不上"和"超时"分开报错
- `js/app.js`
  - `runMap()`：判定条件从 `out.disputes.length` 改为 `out.current`，并接入新增的四组字段
  - `runMap()`：**以 `map.current` 为准回写 `S.verdict` 与 `S.rail`，重绘进度轨**
  - 新增 `noteDegrade()` / `degradeNotice()` / `sourceTag()` / `settledContent()` / `draftContent()`
  - `runSettled()` / `runInsufficient()` 的内容改为优先用本次 AI 产出
  - 删掉 `S.note`（写了但从未显示），换成会渲染出来的 `S.degrades`
- `css/app.css`：新增 `.src-bar` / `.src-tag`（真实 AI / 内置示例 / 已降级 三态）/ `.src-note`
- `tools/drive.js`：新增两个验证阶段 T=50（接口不可达）、T=51（伪 AI 判定已确诊）
- `tools/verify.sh`：新增 2 个阶段、2 份 DOM 快照、13 项断言

**为什么这么做**

做提交前的代码自查，发现真实 AI 这条路有三个问题，**在演示模式下全都看不见**：

1. **判定与流程脱节（最严重）**。界面高亮的是 `map.current`（本次检测结果），
   决定走哪条分支的却是 `S.verdict`（挂号时用关键词猜的）。真实 AI 模式下这两者会不一致
   —— 界面上写着「已确诊、不必会诊」，流程转头就去请人开会诊了。
   这等于把 v1.2 建立起来的「产品会说不用会诊」变成一句假话。
2. **降级是静默的**。三处 AI 调用失败只写 `console.warn`，界面上毫无提示。
   用户以为在看真实 AI 的推理结果，实际看的是内置示例数据。
   路演时若被评委发现，整个产品的可信度就没了。
3. **非会诊分支内容错配**。AI 判定了「已确诊」，给出的却是内置案例里另一道题的共识结论。
   **判定是真的、内容是假的，比全假更糟** —— 因为它更不容易被发现。

关键决策与被否掉的方案：

- **`disputes()` 一次给三组内容**，而不是"先判定、再按判定取内容"。
  后者的隐患是判定与内容可能对不上；一次产出，结构上就不可能错位。
- **验证用"伪 AI"而不是真 Key**（T=51）。注入一个假的 `fetch`，让争议检测返回
  `current: 'settled'`，而首页第一个示例靠关键词本来走会诊。这样能在**完全离线、
  不放任何 Key** 的前提下证明「判定真的改变了流程走向」。比写死一个真 Key 可靠得多。
- **否掉了"只在 console 里记降级"的方案**。理由是用户看不见就等于没说，
  这条也写进了 `docs/02` 的规矩里。

> 🐞 **[已修] 真实 AI 从来没有被调用过（静默失效）**
>    现象：设置里填了 Key、切到「接入真实 AI」、连「测试连接」都提示成功，
>         但走流程时界面上的内容仍是内置剧本，且**没有任何异常提示**。
>    位置：`js/ai.js`（导出）+ `js/app.js` 四处 AI 调用的守卫
>    原因：`ai.js` 用 `const ZHILIAO_AI = ...` 声明，而**顶层 `const` 只进全局词法环境，
>         不会成为 `window` 的属性**。app.js 里的守卫写的是
>         `if (window.ZHILIAO_AI && ZHILIAO_AI.ready())` —— `window.ZHILIAO_AI`
>         恒为 `undefined`，条件永远为假。
>    修法：在 `ai.js` 末尾显式 `window.ZHILIAO_AI = ZHILIAO_AI;`
>    影响：**这是本项目第二个「静默失效」类缺陷**（第一个是 `btn-skip` vs `#btnSkip`）。
>         它比第一个更隐蔽——因为「测试连接」用的是裸标识符，是好的，
>         所以用户会得到"配置成功"的正反馈，更不会怀疑流程里没生效。
>         如果没做 v1.5 这次针对真实 AI 的验证，它会一直留到路演现场。

**验证情况**

```
✓ 静态检查通过（36 个 id，28 处引用全部对齐）
✓ 19 个阶段截图 + 8 份 DOM 快照
✓ 61 项断言全绿（8 组）
```

新增的两组断言里，最有价值的是这几条**否定式**的：

- 真实 AI 接不通时：`src-tag fallback` 出现、降级原因写在界面上、**流程没有卡死**
- 伪 AI 判定已确诊时：**合议消息 = 0**（确实没开会诊）、**进度轨不含「会诊」**、
  共识内容与行动清单都来自模型（`模型给出的共识甲` / `模型给出的第一个动作`）

**遗留问题 / 下一步候选**

- 信息不足分支的行动清单仍用内置案例。它的内容（"先把信息拿回来"）是通用的，

**为什么这么做**

- **素材重新分家**：应用里只放运行时真正要加载的两张图（合计 208 KB，原来 1 MB+）；
  透明底全身图移到 `提交材料/素材/`。应用不需要的东西不该躺在应用目录里
- **头像按色相抠底，不用泛洪**。第一次用 `ImageDraw.floodfill` 失败——它把白色部分吃掉了。
  正确做法是按 HSV 判断「高饱和的蓝」为背景。抠底后头像在浅底深底上都干净，
  PPT 里也能放在任意背景上
- **视频用 Swift + AVFoundation 编码**。系统里的 ffmpeg 是 playwright 的精简版

## 2026-09-12 ｜ v1.3 ｜ 演示稳定化：让路演当场不出事

**本次范围**：`docs/04` 的 v1.3。纯交互与稳定性改动，不碰数据结构。

**为什么这么做**

- **代次机制才是这次的核心，不是"重置按钮"**。原来的重置只清空界面——但上一次流程可能还在 `await` 里，醒来后会继续往**新页面**里塞卡片。不做代次，DoD 里那句「无残留内容」就是空话。这是本轮最有价值的一处改动
- **为什么把「跳到某一阶段」改成「自动演示」**：跳阶段需要另写一套构造中间状态的逻辑，那套逻辑一旦和真实流程有出入，演示出来的就是假东西。自动演示只**替用户点按钮**，复用同一套流程，**不可能脱节**；"跳到第 N 阶段"就等于快速播到那里
- **取消首页输入框的自动聚焦**：焦点一旦落在输入框里，`P`/`R` 这些单键快捷键会全部失效（否则打字会误触发）。演示时快捷键的可用性优先于"少点一次输入框"
- **演示模式只隐藏入口、不改变结构**：录屏看到的必须和现场演示的是同一套界面

**验证情况**

- 另外单独渲染确认了演示模式的外观：设置/帮助入口确实隐藏、右下角提示条正常

**为什么这么做**
- **技术选型选「纯静态本地网页应用」，否掉了 Electron**：用户非技术背景，零安装成本是第一优先级。Electron 要几百 MB 且可能被系统网关拦截，收益仅为"像原生 App"，不划算
- **信息架构选「单页对话流」，否掉了七步七个页面**：用户明确要求"点击少、层级浅、不要藏得深"。七个页面必然产生"返回"按钮和上下文丢失；单页对话流让进度条即页面，永不出现返回
- **配色沿用知乎蓝 #0084FF + 知乎灰阶**，未自创品牌色：方案定位是"知乎生态里的新功能"，视觉上应顺从而非另立
- **病灶必须由用户点选确认，AI 只给假设**：落实方案第 4.2 节——AI 不替用户说出心里话，避免误判与冒犯感
